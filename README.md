# 公交刷卡票价核验台（FastAPI + SQLite + 原生前端）

录入站点分区、票价矩阵、换乘抵扣额、每日封顶额及刷卡记录，系统按卡号配对进出站、
按运营日与换乘规则计算票价，并在数据异常时给出**可定位**的错误且**不生成部分账单**。
另支持**规则试算对比**：输入一组不保存的草案参数，对同一批记录分别按当前配置与草案
计费，逐程与整批对比金额变化；**配对修复预览**：针对缺失进站 / 缺失出站 /
连续同向刷卡，用全局最小编辑搜索生成可完整配对的修复方案（只读，不保存任何改动）；
以及**票价矩阵路径审计**：以分区为节点、已配置的有向票价为边，对实际行程分区对
计算最低成本路径，缺直达票价时给出建议票价与完整路径、直达票价偏贵时标出差额
（只读，不修改矩阵或账单）；以及**行程耗时异常审计**：对已保存且可完整配对的记录
按有向站点对分组，用排除自身的中位数 / MAD 基线标记耗时过长或过短的行程
（只读，不改记录、配置或账单）；以及**站点闸机峰值审计**：按站点与进/出方向
分组，在用户给定的 1～120 分钟窗口内、从实际刷卡时刻起算查找刷卡数最多的
半开区间 [开始, 结束)，返回峰值数量、起止时刻、涉及卡号数与原始行号，
支持设置最低告警数仅标记达标组（只读，不改记录、配置或账单）。
另支持**外部刷卡批次合并预览**：页面粘贴待导入记录并设置 0～120 秒容差，
以已保存记录为基准，仅在卡号、站点、方向相同且时间差不超过容差时建立候选；
按键分组做全局一对一匹配（先最大化配对数，再最小化总时间差，行号稳定破同分），
返回重复配对、仅基准 / 仅导入记录与按时间排序的合并文本（只读，不改记录与账单）。
另支持**匿名客流 OD 发布**：选择运营日起止、15/30/60 分钟初始时间桶与匿名阈值
k（2～50），仅从可完整配对的已保存记录生成「进站 → 出站」聚合；每个运营日、OD
内以去重卡数判定，不足 k 的非空桶反复与前后相邻非空桶合并（优先合并后跨度更小者、
同分选更早邻桶，禁止跨运营日或跨 OD 合并），已无邻桶仍不足 k 则抑制；发布结果只含
最终区间、行程数与去重卡数并可导出 CSV，抑制项只报数量（只读，不改记录、配置或账单）。
另支持**闸机容量排队推演**：选择运营日、1/5/15 分钟桶、每桶通行能力与
最多续算桶数，按站点 × 进/出方向统计已保存刷卡到达量（桶从运营日分界
时刻对齐），按半开桶递推 `处理量=min(期初积压+到达量,容量)`、未处理量
结转，最后一笔后以空桶续算消化、超限未清则标记，展示逐桶到达 / 处理 /
积压与峰值积压、首次超载、清空时刻并支持 CSV 导出（只读，不因配对、
站点或票价错误阻断）。
另支持**通票购买策略回测**：输入若干通票（名称、价格、连续有效运营日数）
与运营日起止，基于最近一次核验生成的账单按卡号比较按次实扣与购买通票；
通票自选定运营日起连续覆盖其有效运营日内全部行程（不因中间无行程暂停），
用动态规划求每张卡总支出最低的购买序列，同价时依次选择通票更少、
首次购买日更早、名称字典序更小的方案，展示基准支出、通票支出、节省额
与逐次购买明细（只读，不改记录、配置或账单）。
另支持**账单争议更正预演**：按原始行号选择同一卡的 1～2 笔已保存记录，
仅临时修改时刻或站点；后端在内存中原子替换后对该卡全部记录重新排序、
配对与计价（不写回记录、配置或账单），以进出站原始行号对为行程标识
对比最近一次核验账单与更正方案，列出新增、移除及金额 / 运营日 / 优惠变化，
并汇总该卡应补收或退款的金额；更正后出现配对、未知站点或缺票价错误时
返回原有定位错误且不产出差额。
另支持**服务中断补偿预览**：页面输入中断站点、起止时刻（闭区间）、
补偿预算与单卡上限；从已保存账单中选出进站或出站发生在该站、且对应
刷卡时刻落在闭区间内的行程，按卡汇总实扣额（整数分）。预算按各卡
实扣额为权重分配，每轮以最大余数补齐整数分（余数相同按卡号排序），
超过单卡上限或该卡实扣额的份额封顶并向未封顶卡重新分配，直到预算
用尽或全部封顶；返回每卡受影响行程数、实扣额、补偿额及未分配金额，
无匹配账单时返回空结果，站点为空 / 区间非法 / 金额非法给出带参数定位的
错误（只读，不改记录、配置或账单）。
另支持**运行中数据库备份下载**：通过 `GET /api/backup` 生成 SQLite
一致性快照并作为文件返回，覆盖站点、票价、刷卡记录、配置及最近账单；
快照经 SQLite 在线备份 API 写入临时文件并通过完整性检查后提供下载，
备份期间即使有并发写入，下载文件也始终对应某一个完整提交点，
且不直接复制正在使用的数据库文件（全程只读，不改业务数据）。

- 后端：FastAPI（Python 3.11）
- 数据库：SQLite（标准库 `sqlite3`，金额以**整数分**存储）
- 前端：原生 HTML / CSS / JavaScript，无框架、无构建步骤
- 部署：Dockerfile + docker-compose，数据持久化到命名卷

## 快速开始

单条启动命令（构建镜像、安装依赖、初始化数据库并后台启动，一条完成）：

```bash
docker compose up -d --build
```

启动后访问 **http://localhost:8000**（端口 **8000**，交互式 API 文档在
http://localhost:8000/docs）。

该命令依次完成：构建镜像并安装依赖 → 启动服务 → 首次启动时自动建库
（SQLite 表结构与默认规则参数由应用启动时初始化），无需任何额外步骤。

配置（**无必填项**，均有默认值，可按需覆盖）：

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `DB_PATH` | `/data/bus.db` | 容器内 SQLite 数据库文件路径；compose 已用命名卷 `bus-data` 持久化 |

端口映射为 `8000:8000`，如需调整宿主机端口，修改 `docker-compose.yml`
中 `ports` 的左侧端口即可。

数据库备份入口：页面右上角 **「⬇ 下载备份」**，或命令行
`curl -OJ http://localhost:8000/api/backup`，即可下载运行中数据库的
SQLite 一致性快照（只读，详见下文 `/api/backup` 一节）。

停止与清理：

```bash
docker compose down          # 停止（保留数据卷）
docker compose down -v       # 停止并删除数据
```

本地裸机运行（不使用 Docker）：

```bash
pip install -r requirements.txt
DB_PATH=./bus.db uvicorn app.main:app --host 0.0.0.0 --port 8000
# 访问地址同样是 http://localhost:8000 （端口 8000）
```

## 业务规则

1. **进出站配对**：刷卡记录按卡号分组、时间升序排列，必须从进站开始且进出成对。
   - 一条进站没有后续出站 → `MISSING_EXIT`（缺失出站）
   - 起始是出站，或出站前没有进站 → `MISSING_ENTRY`（缺失进站）
2. **运营日归属**：行程按**进站时刻**归属运营日，默认以 **04:00** 为分界。
   例如 `2026-09-19 03:20` 的进站属于 `2026-09-18` 运营日。分界时刻可在页面配置。
3. **换乘抵扣**：同一卡号「前次出站 → 下次进站」间隔 **≤ 90 分钟**（可配置）时，
   先抵扣换乘优惠额（默认 1 元，跨运营日的 90 分钟内换乘同样适用）。
   - 抵扣额不超过该程基础票价，最小为 0。
4. **当日封顶**：抵扣之后再按「卡号 + 运营日」应用封顶（默认 10 元/日）。
   - 实扣 = max(0, min(基础票价 − 换乘抵扣, 封顶额 − 当日已累计))
   - 累计额按实扣逐程累加；封顶后后续行程实扣 0。
5. **原子核验**：只要存在任何记录级错误（缺失出站/进站、时间逆序、重复刷卡、
   未知站点、票价矩阵缺项），整批核验失败，**不写入任何账单**（无部分账单）。
   旧账单同时清空，避免过期数据被误读。
6. **重复刷卡 / 时间逆序**：
   - 同卡两条记录时刻完全相同 → `DUPLICATE_SWIPE`（重复刷卡）
   - 同卡出站早于进站、或排序后存在逆序 → `TIME_REVERSED`（时间逆序）
   - 错误信息同时给出卡号、时刻、站点与**原始文本行号**。

账单字段：卡号、卡内序号、运营日、进站/出站时刻、进出站点与分区、
**基础票价、优惠额、优惠来源说明、实扣额、当日累计额（/封顶额）**。

7. **规则试算对比**：在「2. 规则试算对比」区填入一组**不会保存**的草案参数
   （换乘时限、抵扣额、每日封顶、运营日分界），调用试算接口对**当前已保存的同一批
   刷卡记录**分别按当前配置与草案配置计费。
   - 试算与正式核验**完全复用同一套解析、配对与计价规则**，不修改任何配置、
     不写入或清空账单（纯只读）。
   - 任一方案存在错误时（草案参数非法 `CONFIG_BAD`，或数据错误如缺出站、未知站点、
     缺票价等），接口返回 422，`current` / `draft` 两个分块各自携带该方案的
     **原有定位错误**（错误码、行号、卡号、时刻、站点与 `/api/verify` 一致）。
   - 两边均成功时，按**卡号 + 卡内序号**对齐行程，逐程展示运营日（发生归属变化时
     高亮）、当前/草案优惠、当前/草案实扣及差额，并给出每张卡与全批次的实扣、
     优惠合计及差额。差额口径统一为「草案 − 当前」：实扣差额为正表示多付（红），
     为负表示少付（绿）。
8. **配对修复预览**：在「6. 配对修复预览」区对已保存记录一键生成修复方案。
   - 只处理配对结构问题：缺失进站、缺失出站、连续同向刷卡（即核验时的
     `MISSING_ENTRY` / `MISSING_EXIT`）；未知站点、缺票价、时间逆序、重复刷卡等
     非配对错误**按原错误返回**，不生成方案。
   - 记录按卡号分组、卡内按时间升序，做**全局最小编辑搜索**；允许的编辑只有
     **翻转进/出方向**与**删除记录**（各计 1 次编辑），原始时刻、站点、卡号
     一律不改写。修复后的方向序列必然从进站开始严格交替（可完整配对）。
   - 存在多个同成本方案时按**稳定顺序**最多返回 **5** 个，并标明最小编辑数与
     未展示的方案数量；系统**不擅自选定**任何方案。
   - 长批次可用：单卡数千条记录（如 1200 次连续进站，最小编辑 600、方案唯一）
     也能快速返回，最小编辑数与方案总数始终精确，不枚举全部方案。
   - 预览**全程只读**：不保存记录、不写入也不清空账单。页面逐条展示变更、
     修复后的完整记录文本，并提供复制按钮，是否采纳由人工决定。
9. **票价矩阵路径审计**：在「8. 票价矩阵路径审计」区对已保存数据一键审计。
   以分区为节点、已配置的有向票价为边，对已保存刷卡记录配对出的**实际行程
   分区对**计算最低成本路径（整数分 Dijkstra，相同总价按分区序列字典序
   稳定选路，零价边与非对称方向按有向图语义处理）：
   - 缺直达票价但存在可达路径：给出**建议票价**（= 最低成本路径总价）、
     **完整路径**（逐段分区与单价）、**建议补录行**（可复制），以及
     **受影响卡号与原始行号**；
   - 缺直达票价且不可达：保留原 `MISSING_FARE` 定位错误（卡号、行号、
     时刻、站点与 `/api/verify` 一致）；
   - 已有直达票价高于间接路径：标出**差额**（直达 − 间接最低）与
     最低成本路径；
   - 同区行程（如 1→1）按「至少经过一条边」的闭合路径计算，不会把
     「原地不动」当成 0 元路径；
   - 除 `MISSING_FARE` 外的数据错误（未知站点、缺出站、时间逆序等）：
     按 `/api/verify` 的原有定位错误返回，不生成审计结果；
   - 审计**全程只读**：不修改票价矩阵、不写入也不清空账单。
10. **行程耗时异常审计**：在「9. 行程耗时异常审计」区对已保存记录一键审计。
    按（进站站点 → 出站站点）的**有向站点对**分组，行程耗时 = 出站时刻 − 进站时刻：
    - 仅样本数 **≥ 6 程**的站点对参与判定；样本不足的站点对单独列出、不产生标记；
    - 每条行程先从基线中**排除自身**，以其余样本的**中位数**与 **MAD**
      （基线样本相对中位数的绝对偏差的中位数）计算阈值
      **max(10 分钟, 3 × 1.4826 × MAD)**；
    - 绝对偏差**严格大于**阈值时标记为**过长**（高于中位数）或**过短**
      （低于中位数）；结果展示基线样本数、中位数、MAD、阈值、偏差与
      原始进出行号；
    - 判定在秒级精度上进行，展示值换算为分钟（两位小数）；
    - 配对 / 时间类错误（缺失进出站、时间逆序、重复刷卡）按 `/api/verify`
      的原有定位错误返回，不生成审计结果；**未知站点与票价缺项不阻断审计**；
    - 审计**全程只读**：不修改记录、配置，也不写入或清空账单。
11. **站点闸机峰值审计**：在「10. 站点闸机峰值审计」区设置 **1～120 分钟**
    的统计窗口与最低告警数，对已保存记录一键审计。按**站点 × 进/出方向**
    分组，直接统计刷卡记录本身（不依赖配对、站点分区或票价，未知站点不影响统计）：
    - 每组在给定窗口内查找刷卡数最多的**半开区间 `[开始, 结束)`**；
      候选窗口**只从实际刷卡时刻起算**，不做固定整点分桶，跨整点边界的高峰
      （如 08:55～09:05）不会被漏计；边界时刻（结束时刻当刻）的刷卡不计入；
    - 峰值数量并列时，依次按**更早开始时刻**、**站点名**（再按进/出方向）排序；
    - 每组返回**峰值刷卡数、窗口起止时刻、涉及卡号数（去重）、组内总刷卡数与
      窗口内记录的原始文本行号**；峰值刷卡数 **≥ 最低告警数** 的组标记为告警，
      未达标组照常返回但不标记；
    - 页面上原始行号可点击，直接定位到「5. 刷卡记录」中对应行（以已保存数据
      只读回填，不保存任何改动）；
    - 审计**全程只读**：不修改记录、配置，也不写入或清空账单。
12. **外部刷卡批次合并预览**：在「11. 外部刷卡批次合并预览」区粘贴待导入记录并
    设置 **0～120 秒**容差，以已保存记录为基准做只读合并预览。
    - 候选条件：**卡号、站点、进/出方向完全相同**且时间差 **≤ 容差（秒，闭区间）**；
      容差 0 表示必须时刻完全相同。
    - 按（卡号, 站点, 方向）分组做**全局一对一匹配**（稀疏分组用最小费用
      最大流、稠密 / 完整分组用匈牙利算法，费用按 `(时间差, 基准行号,
      导入行号)` 字典序编码）：**先最大化配对数**（未配对罚分高于任意可行
      配对费用之和），**再最小化总绝对时间差**，同分时按基准行号、
      导入行号稳定破同分；匹配是全局最优，不依赖逐条贪心。
    - 结果分三部分返回：**重复配对**（含两侧时刻、行号与时间差）、**仅基准记录**、
      **仅导入记录**；另给出去重后**按时间排序的合并文本**（配对取基准行），
      页面提供一键复制。
    - 待导入文本复用记录解析，`RECORD_BAD_*` 解析错误按粘贴文本行号定位；
      容差非法返回 `CONFIG_BAD`。
    - 预览**全程只读**：不保存待导入记录、不修改已保存记录，也不写入或清空账单。
13. **匿名客流 OD 发布**：在「12. 匿名客流 OD 发布」区选择运营日起止（闭区间，
    按进站时刻归属运营日）、**15 / 30 / 60 分钟**初始时间桶与匿名阈值
    **k（2～50 的整数）**，仅从**已保存且可完整配对**的记录生成「进站 → 出站」聚合。
    - 初始桶按自然日 00:00 整点对齐到所选粒度的网格，半开区间 `[开始, 结束)`；
      行程按**进站时刻**落入初始桶，运营日归属（默认 04:00 分界）与桶网格相互独立。
    - 以**（运营日, 进站站点, 出站站点, 初始桶）**分组，统计每组的**行程数**与
      **去重卡数**；是否发布完全按每个运营日、每个 OD 内的去重卡数判定。
    - 去重卡数 **< k 的非空桶反复与前后相邻的存活非空桶合并**：在左 / 右两个合并
      方向中选择**合并后时间跨度更小**者；跨度相同（同分）时选**更早的邻桶**
      （即左邻桶）；合并后去重卡数取并集、行程数相加并重新参与判定。
      **禁止跨运营日或跨 OD 合并**——合并仅在同一个（运营日, OD）序列内部进行；
      中间空桶不参与合并，但并入后的区间跨度会连续覆盖这些空槽。
    - 某不足 k 的桶在与相邻桶合并后仍不足 k、且**左右均无相邻非空桶**
      （该运营日、OD 内已无其他存活桶）时，整个合并组件被**抑制**：
      不出现在发布结果中，报表仅汇总未能发布的**初始非空桶数与行程数**
      （一个被抑制组件可能覆盖多个初始桶），
      **绝不泄露卡号、原始行号或任何单条时刻**。
    - 页面展示每个最终区间的运营日、进站 / 出站站点、区间起止（结束不含）、
      跨度 / 合并桶数、行程数与去重卡数，可一键**导出 CSV**（含 UTF-8 BOM，
      汇总行只写抑制数量）；所有发布区间的去重卡数均 **≥ k**。
    - 配对 / 时间类错误（`MISSING_ENTRY` / `MISSING_EXIT` / `TIME_REVERSED` /
      `DUPLICATE_SWIPE`）与参数非法（`CONFIG_BAD`：日期格式 / 起止顺序、桶粒度、
      k 范围非法）沿用 `/api/verify` 的**原有定位错误**返回 422，**不产出报表**；
      未知站点（`UNKNOWN_STATION`）与票价缺项（`MISSING_FARE`）**不阻断**发布
      （OD 聚合与站点分区、票价无关）。
    - 发布**全程只读**：不修改记录、配置，也不写入或清空账单。
14. **闸机容量排队推演**：在「13. 闸机容量排队推演」区选择**运营日**、
    **1 / 5 / 15 分钟**时间桶、**每桶通行能力**（人次，正整数）与**最多
    续算桶数**（非负整数），直接统计已保存刷卡记录，按**站点 × 进/出方向**
    分组；时间桶从**运营日分界时刻**起按桶长对齐（半开区间
    `[开始, 结束)`，运营日窗口为当日 `split:00` 至次日 `split:00`）。
    每组按桶递推 **`处理量 = min(期初积压 + 到达量, 容量)`**，
    期末积压 = 期初积压 + 到达量 − 处理量，未处理量结转下一桶；最后一笔
    到达所在桶之后继续追加**零到达空桶**消化积压，直到清零或续算桶数达到
    上限；达到上限仍有积压则该组标记**未清**。页面逐桶展示到达量、期初 /
    期末积压与处理量（运营日桶与续算空桶分色、超载桶与峰值桶高亮），并汇总
    每组**累计到达 / 处理、峰值积压（首次出现时刻）、首次超载时刻、清空
    时刻**，支持一键 **CSV 导出**（UTF-8 BOM，明细为逐桶聚合，不含卡号 /
    行号）。推演只统计记录本身，**不依赖配对、站点分区与票价——任何配对、
    未知站点、票价错误都不阻断**；参数非法（日期格式、桶粒度、容量、续算
    桶数、分界时刻）返回 `CONFIG_BAD`；**全程只读**。
15. **通票购买策略回测**：在「14. 通票购买策略回测」区录入若干通票产品
    （每行 `名称, 价格, 连续有效运营日数`）并选择运营日起止（闭区间，
    最长 3662 天），系统基于**最近一次核验生成的账单**按卡号比较
    「按次实扣」与「购买通票」：
    - 通票自选定运营日起**连续覆盖**其有效运营日内的全部行程，
      **不因中间无行程暂停**；覆盖超出回测范围的天数自动截断；
    - 每张卡的总支出 = 通票价格合计 + 未被覆盖运营日的按次实扣合计，
      用**动态规划**求该支出最低的购买序列；同价时依次选择
      **通票张数更少 → 首次购买日更早 → 名称字典序更小**的方案；
    - 展示每张卡的**基准支出**（范围内按次实扣合计）、**通票方案支出**
      （通票费 + 未覆盖按次）、**节省额**与**逐次购买明细**（购买运营日、
      票名、价格、覆盖运营日起止、覆盖行程数与覆盖行程按次合计），
      以及全部卡合计；
    - 无有效账单（从未成功核验或最近一次核验未产生行程账单）返回
      `NO_BILLS`；日期格式 / 起止顺序 / 范围超长返回 `CONFIG_BAD`；
      产品行格式、重复名称、价格、有效天数非法返回 `PASS_BAD_*` /
      `PASS_DUPLICATE`，产品为空返回 `PASS_EMPTY`；
    - 回测**全程只读**：不修改记录、配置，也不写入或清空账单。
16. **账单争议更正预演**：在「15. 账单争议更正预演」区按**原始行号**
    （第 5 区「来源行」）选择同一卡的 **1～2 笔**已保存记录，仅可临时
    修改**时刻**或**站点**（每项留空表示不修改）：
    - 后端在内存中对修正记录做**原子替换**（新建记录对象，不改原数据），
      对该卡全部记录按时刻**重新排序**后复用 `verify()` 重新配对与计价；
      全程**只读**：不写回记录、配置或账单；
    - 以**（进站原始行号, 出站原始行号）对**作为行程标识，对比最近一次
      核验账单与更正方案：新增、移除、变化（时刻 / 站点 / 运营日 /
      基础票价 / 优惠 / 实扣 / 当日累计）与不变逐行程列出并高亮；
    - 汇总该卡实扣合计差额（差额 = 更正后 − 当前）：差额为正为
      **应补收**，为负为**应退款**；
    - 更正后出现配对、未知站点或缺票价等错误时，返回 `verify()` 的
      **原有定位错误**且不产出任何差额；
    - 跨卡选择（`DISPUTE_CROSS_CARD`）、重复行号
      （`DISPUTE_LINE_DUPLICATE`）、行号不存在
      （`DISPUTE_LINE_UNKNOWN`）、未给出修改值（`DISPUTE_BAD_FIELDS`）、
      时刻值非法（`DISPUTE_BAD_TIME`）、更正笔数非法
      （`DISPUTE_EDIT_COUNT`）返回明确错误；无有效账单时返回
      `NO_BILLS`。
17. **服务中断补偿预览**：在「16. 服务中断补偿预览」区输入中断**站点**、
    **起止时刻**（闭区间）、**补偿预算**与**单卡上限**（金额单位：元，
    计算时统一按整数分）。
    - 从**最近一次核验生成的账单**中选出「**进站或出站**发生在该站、
      且对应刷卡时刻落在 **[开始, 结束] 闭区间** 内」的行程；同一行程
      进出站都匹配时只计一次，按卡汇总**实扣额**（整数分权重）。
    - 每卡的有效上限为 **min(单卡上限, 该卡实扣额)**——补偿既不超过
      设定的单卡上限，也不超过该卡的实际支出。
    - 分配按轮进行：先以各卡实扣额为权重按比例分配当前可用预算，
      每轮按**最大余数法**把份额补齐为整数分（先 floor，剩余分按余数
      从大到小逐卡补 1；**余数相同按卡号字典序**）；超过有效上限的
      份额**封顶**，溢出的分数进入下一轮**仅向未封顶卡**重新分配
      （权重仍为各卡实扣额），直到**预算用尽或全部卡封顶**。
    - 返回每卡**受影响行程数、实扣额、补偿额、未补偿（实扣−补偿）、
      有效上限与封顶状态**（`cap`=单卡上限封顶 / `charged`=实扣额封顶），
      以及全局**补偿合计与未分配金额**；无匹配账单（含从未核验）时
      `cards=[]`、未分配金额等于预算全额，仍返回 200。
    - 站点为空返回 `COMP_BAD_STATION`；时刻无法解析、起始晚于结束、
      预算或单卡上限为负 / 非有限数字返回 `CONFIG_BAD`；错误的
      `location.param` 指明出错参数（`station` / `start_time` /
      `end_time` / `budget` / `per_card_cap`）。
    - 预览**全程只读**：不修改记录、配置，也不写入或清空账单。

## 录入格式

页面上每个区块都是「每行一条」的纯文本，分隔符支持逗号、制表符、分号、空白与全角逗号；
空行与 `#` 开头的注释行会被忽略。

| 区块 | 每行格式 | 示例 |
|---|---|---|
| 站点分区 | `站点名, 分区号` | `科技园, 1` |
| 票价矩阵 | `起始分区, 到达分区, 票价` | `1, 2, 3.00`（按方向精确匹配） |
| 刷卡记录 | `卡号, 时刻, 站点, 进/出` | `A001, 2026-09-18 08:00:00, 科技园, 进` |

- 刷卡方向：`IN` / `进` / `进站` 或 `OUT` / `出` / `出站`。
- 时刻格式：`YYYY-MM-DD HH:MM[:SS]`、`YYYY/MM/DD HH:MM`、`YYYY-MM-DDTHH:MM:SS`、
  或月日格式 `MM-DD HH:MM`（自动补当前年份）。
- 站点名与分区、矩阵项均不可重复定义；刷卡记录中的重复刷卡是业务校验，
  在「运行核验」时报告。

### `/api/trial-compare` 规则试算对比

请求体为**草案参数**（均必填；数值合法性由核心层校验，非法时返回 422 +
`CONFIG_BAD`，而不是请求体校验错误）：

```json
{
  "transfer_minutes": 120,
  "transfer_discount": 2.00,
  "daily_cap": 15.00,
  "day_split_hour": 5
}
```

两方案均成功时返回 `200`：

`trip_bill`。

### `/api/repair-preview` 配对修复预览

无请求体。针对**已保存**的刷卡记录做全局最小编辑搜索，返回可完整配对的修复方案。
全程只读：不保存记录、不写入或清空账单。

记录已配对时（无需修复）：

```json
{ "ok": true, "min_edits": 0, "total_plans": 0,
```

### `/api/od-flow-publish` 匿名客流 OD 发布

请求体四个参数；数值 / 日期合法性由核心层校验，非法时返回 422 + `CONFIG_BAD`：

```json
{ "ok": false,
```

页面「⬇ 导出 CSV」按钮把当前发布结果在浏览器端导出为 CSV（UTF-8 BOM，
汇总行仅写抑制数量），不经过任何额外的后端写接口。

- 每个桶为半开区间 **`[start_time, end_time)`**，`bucket_index` 为相对
  运营日窗口起点（分界时刻）的桶序号；`continuation=true` 表示最后一笔
  到达之后追加的**零到达空桶**（可越过窗口末端，仍沿同一桶网格）。
- 递推口径：**处理量 = min(期初积压 + 到达量, 容量)**，
  `end_backlog = begin_backlog + arrival_count − processed_count`；
  `overloaded=true` 当且仅当「期初积压 + 到达量」严格大于容量。
- `peak_backlog` / `peak_time`：全部桶中最大的**期末积压**及其首次出现的
  桶起点；`first_overload_time`：第一个超载桶的起点（从未超载为 `null`）；
  `clear_time`：积压最后一次**由正转 0** 的桶结束时刻——全程从未积压的组
  为 `null`。
- `cleared=false` 时给出 `remaining_backlog`（续算上限用完后仍未处理的
  积压量）与 `extra_buckets_used`；`groups[]` 按峰值积压降序、首次超载
  时刻升序（从未超载排后）、站点名、方向稳定排序。
- 窗口内无任何记录时 `groups=[]`，仍返回 `200`。

参数非法时返回 HTTP 422（不改任何数据）：

```json
{ "ok": false,
  "errors": [ { "code": "CONFIG_BAD",
                "message": "时间桶粒度必须是 (1, 5, 15) 之一（分钟），实际：10" } ] }
```

推演为只读操作：只执行 SELECT 与内存递推，不修改记录、配置，也不写入或
清空账单。页面「⬇ 导出 CSV」在浏览器端基于同一 JSON 导出逐桶明细与每组
汇总（UTF-8 BOM），明细只有桶级聚合，不含卡号或原始行号，也没有额外的
后端写接口。

### `/api/pass-backtest` 通票购买策略回测

请求体为通票产品文本（每行 `名称, 价格, 连续有效运营日数`，与站点 / 票价
录入共用分隔符与 `#` 注释规则）与运营日起止（`YYYY-MM-DD`，**闭区间**，
最长 3662 天）：

```json
{
  "passes_text": "一日票, 6.00, 1\n三日票, 15.00, 3",
  "start_day": "2026-09-18",
  "end_day": "2026-09-20"
}
```

回测基于**最近一次核验生成的账单**（与 `GET /api/bills` 同源），只统计
运营日落在起止范围内的行程。通票自购买运营日起**连续覆盖**其有效运营日
内的全部行程，不因中间无行程暂停；每张卡用动态规划求
「通票费 + 未覆盖按次实扣」最低的购买序列，同价时依次按
**通票张数更少 → 首次购买日更早 → 名称字典序更小**破同分。
返回 `200` 时的结构：

```json
{
  "ok": true,
  "start_day": "2026-09-18",
  "end_day": "2026-09-20",
  "day_count": 3,
  "last_verified_at": "2026-09-20 12:00:00",
  "trip_count": 5,
  "card_count": 2,
  "baseline_total": 13.0,
  "pass_cost_total": 6.0,
  "uncovered_total": 3.0,
  "pass_total": 9.0,
  "saving_total": 4.0,
  "passes": [ { "name": "一日票", "price": 6.0, "valid_days": 1 } ],
  "cards": [
    {
      "card": "A001",
      "trip_count": 4,
      "baseline_total": 10.0,
      "pass_cost": 6.0,
      "uncovered_total": 0.0,
      "pass_total": 6.0,
      "saving": 4.0,
      "purchase_count": 1,
      "purchases": [
        {
          "day": "2026-09-18",
          "name": "一日票",
          "price": 6.0,
          "valid_days": 1,
          "cover_start": "2026-09-18",
          "cover_end": "2026-09-18",
          "covered_days": 1,
          "covered_trip_count": 4,
          "covered_baseline": 10.0
        }
      ]
    }
  ]
}
```

- `baseline_total`：范围内各卡按次实扣合计（基准支出）；`pass_total`：
  最优购买序列下的总支出（= `pass_cost_total` 通票费 + `uncovered_total`
  未覆盖运营日按次实扣）；`saving_total = baseline_total − pass_total`
  （恒 ≥ 0，「全程不买」始终是可行解）。
- `cards[].purchases[]`：逐次购买明细（购买运营日、票名、价格、有效天数、
  覆盖运营日起止 `cover_start`～`cover_end`、覆盖行程数与这些行程的按次
  实扣合计）；同一卡的购买区间两两不重叠。
- 范围内没有行程时 `cards=[]`、各项合计为 0，仍返回 `200`。

无有效账单、日期或产品非法时返回 HTTP 422（不改任何数据）：

```json
{ "ok": false,
  "errors": [ { "code": "NO_BILLS",
                "message": "尚未生成有效账单：请先在「7. 核验结果」成功运行核验，…" } ] }
```

- `NO_BILLS`：从未成功核验，或最近一次核验未产生任何行程账单；
- `CONFIG_BAD`：运营日格式错误、起始晚于结束、范围超过 3662 天；
- `PASS_BAD_FIELDS` / `PASS_BAD_PRICE` / `PASS_BAD_DAYS` / `PASS_DUPLICATE`：
  通票产品行格式、价格、有效天数非法或名称重复（`location.line` 指向
  产品文本行号）；`PASS_EMPTY`：未录入任何通票产品。

回测为只读操作：只执行 SELECT 与内存动态规划，不修改记录、配置，
也不写入或清空账单。

### `/api/dispute-preview` 账单争议更正预演

请求体为 **1～2 笔更正**（`edits` 数组，须为同一卡的记录）：每笔按
**原始行号**（`line`，即第 5 区「来源行」）选择一笔已保存记录，
仅可临时修改**时刻**（`time`）或**站点**（`station`），两者均可选、
至少给出其一；数值与结构合法性由核心层校验，非法时返回 422 +
`DISPUTE_*` 定位错误：

```json
{
  "edits": [
    { "line": 3, "time": "2026-09-18 09:45:00" },
    { "line": 4, "station": "中心公园" }
  ]
}
```

后端在内存中**原子替换**（新建修正记录，不改动已保存数据），对该卡全部
记录按时刻**重新排序**后复用 `verify()` 重新配对与计价，再以
**（进站原始行号, 出站原始行号）对**为行程标识，对比**最近一次核验账单**
（与 `GET /api/bills` 同源）与更正方案。返回 `200` 时的结构：

```json
{
  "ok": true,
  "card": "B002",
  "last_verified_at": "2026-09-26 12:00:00",
  "edits": [
    { "line": 10, "card": "B002", "action": "OUT", "direction": "出",
      "old_time": "2026-09-19 03:45:00", "new_time": null,
      "old_station": "中心公园", "new_station": "大学城",
      "detail": "第 10 行（B002 2026-09-19 03:45:00 @ 中心公园 出）：站点 中心公园 → 大学城" }
  ],
  "trips": [
    {
      "entry_line": 9, "exit_line": 10, "trip_key": "9→10",
      "status": "changed",
      "current":   { "operating_day": "2026-09-18", "entry_time": "…",
                     "charged_fare": 3.0, "discount": 0.0, "…": "…" },
      "corrected": { "operating_day": "2026-09-18", "entry_time": "…",
                     "charged_fare": 4.0, "discount": 0.0, "…": "…" },
      "charge_diff": 1.0, "discount_diff": 0.0,
      "day_changed": false,
      "changed_fields": ["station", "base_fare", "charged_fare", "daily_cumulative"]
    }
  ],
  "summary": {
    "current_total": 3.0, "corrected_total": 4.0, "delta": 1.0,
    "kind": "surcharge",
    "current_discount_total": 0.0, "corrected_discount_total": 0.0,
    "discount_delta": 0.0,
    "trip_count_current": 1, "trip_count_corrected": 1,
    "added_count": 0, "removed_count": 0, "changed_count": 1, "same_count": 0
  }
}
```

- `trips[].status`：`added`（行号对只在更正方案中出现）、`removed`
  （只在当前账单中出现）、`changed`（两侧都有且字段有差异）、`same`
  （两侧一致）；`current` / `corrected` 为该侧账单视图（新增 / 移除侧
  为 `null`），`changed_fields` 列出差异字段（`time` / `station` /
  `operating_day` / `base_fare` / `discount` / `charged_fare` /
  `daily_cumulative`），供页面高亮。
- `charge_diff` / `discount_diff` 口径为「更正后 − 当前」：新增计全额、
  移除计负额，因此**逐程差额之和恒等于该卡合计差额** `summary.delta`；
  `summary.kind` 为 `surcharge`（应补收，delta>0）/ `refund`
  （应退款，delta<0）/ `none`（差额为 0）。
- `trips` 按（进站行号, 出站行号）升序排列；`edits` 为实际应用的更正
  明细（含原值 / 新值与可读描述）。

更正后出现配对、未知站点或缺票价等错误时返回 HTTP 422，
错误对象与 `/api/verify` **完全一致**（原有定位错误），且不产出任何差额；
请求本身非法时返回 `DISPUTE_*` 明确错误：

```json
{ "ok": false, "card": "A001", "edits": [],
  "errors": [ { "code": "DISPUTE_CROSS_CARD",
                "message": "更正预演只能选择同一张卡的记录，实际涉及卡号：A001、B002" } ] }
```

- `DISPUTE_EDIT_COUNT`：更正笔数不是 1～2；`DISPUTE_LINE_UNKNOWN`：
  行号不是正整数或已保存记录中不存在；`DISPUTE_LINE_DUPLICATE`：
  重复选择同一行号；`DISPUTE_CROSS_CARD`：两笔更正分属不同卡；
  `DISPUTE_BAD_FIELDS`：某笔更正未给出任何修改值；
  `DISPUTE_BAD_TIME`：新时刻格式无法识别；`NO_BILLS`：尚未生成有效账单。
- 预演为只读操作：只执行 SELECT 与内存计算，不写回记录、配置，
  也不写入或清空账单。

### `/api/compensation-preview` 服务中断补偿预览

请求体五个参数；合法性由核心层校验，非法时返回 422（错误的
`location.param` 指明出错参数），而不是请求体校验错误：

```json
{
  "station": "科技园",
  "start_time": "2026-09-18 07:56:00",
  "end_time": "2026-09-18 08:10:00",
  "budget": 12.00,
  "per_card_cap": 2.00
}
```

- `station`：中断站点名，不可为空（空字符串 / 空白返回
  `COMP_BAD_STATION`）。
- `start_time` / `end_time`：中断起止时刻，支持与刷卡记录同一组时刻
  格式（`YYYY-MM-DD HH:MM[:SS]` 等）；无法解析或起始晚于结束返回
  `CONFIG_BAD`；区间为**闭区间**，起止边界时刻当刻的刷卡计入。
- `budget` / `per_card_cap`：补偿预算与单卡上限（元，≥ 0 的有限数字）；
  传入值先按四舍五入换算为**整数分**参与全部计算，输出金额仍为元
  （两位小数）。

从**最近一次核验账单**（与 `GET /api/bills` 同源）中选出「进站或出站
发生在该站、且对应刷卡时刻落在闭区间内」的行程，按卡汇总实扣额后做
**权重分配 + 逐轮封顶重分**。返回 `200` 时的结构：

```json
{
  "ok": true,
  "station": "科技园",
  "start_time": "2026-09-18 07:56:00",
  "end_time": "2026-09-18 08:10:00",
  "budget": 12.0,
  "per_card_cap": 2.0,
  "last_verified_at": "2026-09-26 12:00:00",
  "trip_count": 6,
  "card_count": 6,
  "charged_total": 20.0,
  "compensated_total": 12.0,
  "uncompensated_total": 8.0,
  "unallocated": 0.0,
  "round_count": 2,
  "cards": [
    {
      "card": "A001",
      "trip_count": 1,
      "charged_total": 3.0,
      "compensation": 2.0,
      "uncompensated": 1.0,
      "effective_cap": 2.0,
      "capped": true,
      "cap_reason": "cap"
    }
  ]
}
```

- 分配规则（全程整数分）：
  1. 各卡有效上限 `effective_cap = min(per_card_cap, charged_total)`；
  2. 每轮以**未封顶卡的实扣额**为权重按比例分配当前可用份额
     （`floor(份额·权重/权重和)`），再用**最大余数法**按余数从大到小
     逐卡补 1 分补齐整数，**余数相同按卡号字典序**；
  3. 本轮超过有效上限的份额截断封顶，溢出分数进入下一轮仅向未封顶卡
     重新分配（权重仍为实扣额）；重复直到**预算用尽（无溢出）或全部卡
     封顶**，此时剩余预算计入 `unallocated`。
- `cards[]` 按卡号字典序排列；`capped=true` 表示该卡已达到有效上限，
  `cap_reason` 为 `cap`（被单卡上限封顶）或 `charged`（被该卡实扣额
  封顶）；`uncompensated = charged_total − compensation` 为该卡实扣中
  未被补偿的部分。
- 汇总恒等式：`compensated_total + unallocated = budget`；且
  `compensated_total ≤ min(budget, 全部受影响卡实扣合计)`。
- **无匹配账单**（从未核验、账单为空或该站 / 区间内无行程）时正常
  返回 200：`cards=[]`、各卡合计为 0、`unallocated = budget`。
- 站点未在站点分区中定义不算错误（账单只按站点名匹配），无该名账单时
  即空结果；参数非法时返回 HTTP 422：

```json
{ "ok": false,
  "errors": [
    { "code": "COMP_BAD_STATION", "message": "站点不能为空",
      "location": { "param": "station" } },
    { "code": "CONFIG_BAD",
      "message": "起始时刻不能晚于结束时刻：2026-09-18 09:00:00 ～ 2026-09-18 08:00:00",
      "location": { "param": "start_time" } },
    { "code": "CONFIG_BAD",
      "message": "补偿预算必须是不小于 0 的有限数字（元）：-1",
      "location": { "param": "budget" } }
  ] }
```

预览为只读操作：只执行 SELECT 与内存计算，不修改记录、配置，
也不写入或清空账单。

### `/api/backup` 数据库备份下载

无请求体。生成**运行中数据库**的一致性快照并作为文件返回
（`Content-Disposition: attachment`，文件名形如
`bus-backup-20260926-120000.db`，标准 SQLite 数据库文件）。

- 快照覆盖**站点分区、票价矩阵、刷卡记录、规则参数与最近一次核验账单**
  （即 `station` / `fare` / `swipe` / `meta` / `trip_bill` 全部内容）；
- 使用 **SQLite 在线备份 API**（分块复制 + 页间休眠）生成快照：备份期间
  即使有并发写入，下载文件也始终对应源库**某一个完整提交点**
  （事务边界），绝不直接复制正在使用的数据库文件；
- 快照先写入**临时文件**，通过 `PRAGMA integrity_check` 完整性检查后
  才提供下载；临时文件在响应结束（或失败）后自动清理，不会残留；
- 备份**全程只读**：源库以只读方式（`mode=ro`）打开，不修改任何业务数据；
- 页面入口：右上角 **「⬇ 下载备份」**；命令行示例：
  `curl -OJ http://localhost:8000/api/backup`；
- 快照生成失败时返回 HTTP 500，不产生下载文件。

下载的 `.db` 文件可直接作为 SQLite 数据库打开核对，或在需要时替换
`/data/bus.db`（容器内路径，可用 `DB_PATH` 覆盖）完成恢复。

## 实现说明

- **金额精度**：业务层以元计算并保留两位小数；落库统一转整数分，避免浮点误差。
- **事务原子性**：整批替换基础数据、核验写账单均在单事务内完成；核验失败时清空
  `trip_bill`，因此任何时刻读到的账单要么是上一次完整成功的结果，要么为空。
  `/api/trial-compare`、`/api/repair-preview`、`/api/fare-path-audit`、
  `/api/duration-audit`、`/api/station-peak-audit`、
  `/api/external-merge-preview`、`/api/od-flow-publish`、
  `/api/pass-backtest`、`/api/dispute-preview` 与
  `/api/compensation-preview` 全程只执行 SELECT，
  不调用任何写接口，配置、矩阵、记录与账单均保持不变
  （`/api/gate-queue-sim` 同样只执行 SELECT + 内存递推）。
- **试算复用**：试算接口直接调用核心层 `trial_compare()`，内部对两套配置各执行一次
  `verify()`，再按 `(卡号, 卡内序号)` 对齐账单；因此配对、运营日归属、换乘抵扣与
  封顶规则与正式核验永远一致，不会出现两套口径。
- **修复搜索**：修复预览先用 `verify()` 分离出配对类错误（`MISSING_ENTRY` /
  `MISSING_EXIT`），其余错误原样返回；随后按卡分组、卡内按时间升序，用
  动态规划求最小编辑数与方案数（每条记录 keep / flip / delete，保留序列须进出
  交替），再借助方案计数表**迭代**构造字典序（keep < flip < delete）前 5 个
  操作序列——不递归（单卡数千条记录也不会触及递归深度上限），也不先枚举
  全部方案再截断（方案数随记录数指数增长时，展开耗时仍与记录数成线性）。
  各卡独立，全局最小编辑数为各卡之和，方案总数为各卡方案数之积；多卡组合
  按卡号升序、后卡方案变化最快展开，同样只物化前 5 个组合。
- **路径审计**：`fare_path_audit()` 复用 `verify()` 配对出的行程
  （`VerifyResult.trips`），除 `MISSING_FARE` 外的错误原样拦截返回。
  对每个实际行程分区对的起始分区跑一次 Dijkstra：边权为整数分（非负，
  零价边合法），堆键为 `(成本, 分区序列)`，因此相同总价按分区序列字典序
  稳定选路，且结果必为简单路径；边是有向的，非对称票价不会互相干扰。
  同区对（z→z）不允许零条边的「原地 0 元」，用「不重返起点的最短路 +
  枚举最后一条回边」求最低成本闭合路径。建议票价 = 最低成本路径总价；
  直达偏贵当且仅当 直达分 > 最低成本分（整数分精确比较，无浮点误差）。
- **耗时审计**：`duration_audit()` 复用 `verify()` 配对出的行程
  （`VerifyResult.trips`），仅配对 / 时间类错误（缺失进出站、时间逆序、
  重复刷卡）会阻断审计并原样返回定位错误；未知站点与票价缺项不阻断
  （耗时与分区、票价无关）。按（进站站点 → 出站站点）有向站点对分组后，
  仅样本数 ≥ 6 的组参与判定：每条行程排除自身，以其余样本的中位数与
  MAD（绝对偏差的中位数）计算阈值 max(10 分钟, 3 × 1.4826 × MAD)，
  绝对偏差严格大于阈值才标记为过长 / 过短；判定在秒级精度上进行，
  分钟值（两位小数）仅用于展示。
- **峰值审计**：`station_peak_audit()` 直接统计已保存的 `Swipe` 记录，
  不经过 `verify()`，因此与配对结构、站点分区、票价、运营日配置完全无关
  （审计不产生数据类错误，参数非法沿用 `CONFIG_BAD`）。按（站点, 方向）
  分组后组内按 `(时刻, 行号)` 稳定排序，以每个实际刷卡时刻为候选起点做
  滑动窗口：右指针只进不退，窗口为 `[t, t + W)` 的半开区间（datetime
  精确比较，边界时刻当刻不计入），因此时间复杂度为 O(n)，且跨整点边界的
  高峰不会像固定分桶那样被切漏。峰值并列时只保留扫描中第一个最大值，
  天然对应更早起点；组间再按峰值降序、开始时刻、站点名、方向排序。
  `card_count` 用集合去重，`lines` 为窗口内记录的原始行号（升序）。
- **合并预览**：`external_merge_preview()` 以待导入文本复用
  `parse_records_text()` 解析（默认补当前年），以已保存 `Swipe` 为基准，
  按（卡号, 站点, 方向）分组成互不相交的候选域：各域独立求解，域内最优
  即全局最优。候选边按两侧时刻排序后滑动窗口生成（只枚举 `|Δt| ≤ 容差`
  的对），并先剔除孤立点压缩子图；候选边费用编码为整数
  `时间差·B1 + 基准行号·B2 + 导入行号`，进位基 `B1/B2` 取大于任意行号
  总和的值，使整数比较等价于「配对数 → 总时间差 → 基准行号和 →
  导入行号和」的字典序目标。稀疏域用最小费用最大流（Johnson 势 +
  Dijkstra，源→基准→候选导入→汇），稠密 / 完整域用带「不配对」虚拟列的
  匈牙利算法（虚拟列罚分高于任意可行配对费用之和，故先最大化配对数）。
  匹配是全局最优，逐条贪心无法保证该最优性；真实数据中同卡同站同向且
  容差仅 0～120 秒，分组很小、候选稀疏。合并文本取「配对基准记录 +
  仅基准 + 仅导入」，按 `(时刻, 卡号, 站点, 方向, 来源, 行号)` 排序，
  来源次序使同时刻记录中基准在前。
- **匿名 OD 发布**：`od_flow_publish()` 复用 `verify()` 配对出的行程
  （`VerifyResult.trips`），仅配对 / 时间类错误与配置错误
  （`MISSING_ENTRY` / `MISSING_EXIT` / `TIME_REVERSED` / `DUPLICATE_SWIPE` /
  `CONFIG_BAD`）阻断发布并原样返回定位错误；未知站点与票价缺项不阻断
  （OD 聚合只依赖站点名与进出站时刻）。参数（运营日起止闭区间、
  15/30/60 分钟桶、k=2～50）非法时统一返回 `CONFIG_BAD`，不产出报表。
  初始桶以自然日 00:00 为起点对齐到桶网格，行程按进站时刻落桶；运营日归属
  （默认 04:00 分界）只作为分组键，因此跨分界的凌晨桶与当日同名桶被运营日键
  天然隔离，绝不会跨运营日合并。每个（运营日, OD）序列独立执行
  **k-匿名桶合并**：状态为按起点排序的存活组件（含起点 / 终点 / 去重卡集合 /
  行程数 / 覆盖的初始非空桶数），每轮取最靠左的去重卡数 < k 的组件，
  比较「并入左邻」「并入右邻」两种合并的跨度秒数取较小者，等跨度取更早的
  左邻；左 / 右均无邻桶时删除（抑制），并按组件覆盖的初始桶数累计抑制统计。处理顺序固定（始终最左）且同分固定向左，
  结果与录入顺序无关、可复现。输出只含桶粒度的区间起止、行程数与去重卡数，
  响应中不含卡号、原始行号、单条时刻；CSV 由浏览器端基于同一 JSON 生成
  （UTF-8 BOM），后端无任何写接口。
- **闸机排队推演**：`gate_queue_sim()` 直接统计已保存的 `Swipe` 记录，
  不经过 `verify()`，因此与配对结构、站点分区、票价、运营日归属判定均无关
  （不产生任何数据类错误；运营日 / 桶 / 容量 / 续算桶数 / 分界时刻非法时
  统一返回 `CONFIG_BAD`）。运营日窗口为
  `[当日 split:00, 次日 split:00)`，桶序号
  `idx = floor((t − 窗口起点) / 桶长秒)`，三种粒度 1 / 5 / 15 均整除 1440，
  因此桶网格严格从分界时刻对齐（跨分界的凌晨刷卡进入当日序号较大的桶，
  绝不与前一运营日混淆）。按（站点, 方向）聚合桶到达量后，从每组首笔到达
  桶到末笔到达桶逐桶递推 `处理量 = min(期初积压 + 到达量, 容量)`，
  中间空槽照常输出（积压在无到达桶中继续消化）；末笔之后再追加至多
  `max_extra_buckets` 个零到达续算桶（可越过窗口末端、仍沿同一网格），
  提前清零即停止，用满仍有积压则 `cleared=false`。峰值积压取所有桶
  期末积压的最大值并记录首次出现的桶起点，首次超载取首个
  「需求 > 容量」的桶，清空时刻为积压最后一次由正转 0 的桶结束时刻
  （全程未积压为 null）。组间按峰值降序、首次超载时刻、站点名、方向稳定
  排序。CSV 由浏览器端基于同一 JSON 生成（UTF-8 BOM），明细只到桶级聚合。
- **通票回测**：`pass_backtest()` 只读取 `trip_bill` 账单（`db.list_bills`），
  不重新核验、不依赖站点 / 票价 / 配置，因此核验之后修改数据不会污染
  回测口径（账单失效时 `last_verified_at` 已被清空，回测直接报
  `NO_BILLS`）。金额全程整数分：账单实扣（元）转分后按
  （卡号, 运营日）汇总为逐日按次支出，通票价格同样转分。
  每卡独立做动态规划：`f[i]` 为第 i 个运营日起的最优键
  （支出, 张数, 首次购买日, 首张名称），转移为「第 i 天按次实扣」或
  「第 i 天购买通票 p 并跳到 min(i+有效天数, 范围末)」；覆盖连续有效、
  不因中间无行程暂停，超出范围的天数自动截断。破同分严格按
  支出 → 张数 → 首次购买日 → 名称字典序：同一状态下各购买选项的
  首次购买日相同而名称互不相同（名称唯一），名称字典序在首元素即可
  决出，故四元键完整充分（已用随机小样本与暴力枚举全量对拍验证）。
  重构购买序列后逐次统计覆盖运营日起止、覆盖行程数与这些行程的按次
  实扣合计；`pass_total = 通票费 + 未覆盖按次`，
  `saving = baseline − pass_total ≥ 0`（全程不买恒为可行解）。
  重叠购买可被不重叠方案不增成本地替代，故 DP 只枚举不重叠序列
  不损失最优性。回测只执行 SELECT，不修改记录、配置或账单。
- **争议更正预演**：`dispute_preview()` 先校验更正请求（1～2 笔、
  行号为正整数且存在于已保存记录、不重复、同一卡、每笔至少修改
  时刻或站点之一、时刻格式可解析），再在内存中新建修正后的 `Swipe`
  对象（原对象不被改动）完成原子替换，对该卡全部记录按 `(时刻, 行号)`
  重新排序，与其他卡记录一起复用 `verify()` 重新配对计价——更正后的
  配对、未知站点、缺票价等错误即 `verify()` 的原有定位错误，直接返回
  且不产出差额。成功时以 `(进站原始行号, 出站原始行号)` 为行程标识
  对齐当前账单（`trip_bill`，与 `GET /api/bills` 同源）与更正方案：
  行号对只在更正方案中出现为新增、只在当前账单中出现为移除、两边都有
  则逐字段（时刻 / 站点 / 运营日 / 基础票价 / 优惠 / 实扣 / 当日累计）
  判定变化；差额口径为「更正后 − 当前」，新增计全额、移除计负额，
  逐程差额之和恒等于该卡合计差额（`delta>0` 应补收、`<0` 应退款）。
  全程只执行 SELECT 与内存计算，不写回记录、配置或账单。
- **服务中断补偿预览**：`compensation_preview()` 只读取 `trip_bill`
  账单（`db.list_bills`），不重新核验、不依赖站点 / 票价 / 配置。
  匹配按账单字段直接判定：`entry_station == 站点` 且进站时刻落在
  闭区间，或 `exit_station == 站点` 且出站时刻落在闭区间（同一行程
  两端都命中只计一次）；时刻为 `YYYY-MM-DD HH:MM:SS` 文本解析后按
  datetime 闭区间比较。金额全程整数分：预算与单卡上限先换算为分，
  各卡实扣额（分）为权重。分配按轮进行——每轮把当前可用份额按
  `floor(份额·权重/权重和)` 分摊，余数从大到小逐卡补 1 分（最大余数
  法，余数相同按卡号字典序），使本轮恰好分完可用份额；随后对每卡
  按 `min(单卡上限, 实扣额)` 截断封顶，溢出分数进入下一轮仅向未封顶
  卡重分。每轮要么溢出为 0（预算用尽）要么至少一张卡封顶退出，
  故至多「受影响卡数」轮内终止；全部封顶后剩余预算即 `unallocated`。
  实扣为 0 的卡权重为 0、不参与分配但仍按 0 补偿列出；无匹配账单时
  `cards=[]` 且未分配金额等于预算全额。已用 500 组随机样本对拍验证
  守恒不变式（补偿 + 未分配 = 预算、每卡补偿 ≤ min(上限, 实扣)、
  存在未封顶正权重卡时预算必用尽）。全程只执行 SELECT 与内存计算，
  不修改记录、配置或账单。
- **数据库备份**：`/api/backup` 使用 SQLite 在线备份 API
  （`Connection.backup`，分块复制并在页间短暂休眠）把运行中的数据库
  复制到临时文件：源库以只读 URI（`mode=ro`）打开，备份期间并发写入
  可继续提交，SQLite 会重传被改动的页，因此快照始终对应源库某一个
  完整提交点，而不是对正在使用的数据库文件做逐字节拷贝。快照通过
  `PRAGMA integrity_check` 完整性检查后才作为附件返回；临时文件由
  响应对象在发送结束（无论成功或失败）后删除。全程不执行任何业务
  写操作。
- **数据位置**：容器内 `DB_PATH=/data/bus.db`，compose 用命名卷 `bus-data` 持久化；
  可用环境变量 `DB_PATH` 覆盖路径。
- **无外部前端依赖**：页面由 FastAPI 直接以静态文件提供，无需 npm/CDN，
  离线网络下也可使用。
